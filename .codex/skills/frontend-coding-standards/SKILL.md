# 前端开发规范

本 Skill 用于本项目的前端实现和评审，是决策指南，不扩大用户需求范围，也不替代
仓库 `AGENTS.md` 中的流程、安全和权限约束。

## 使用其他 Skill

当需求包含页面、组件、仪表盘、工作台或其他界面的视觉设计、布局创新、交互美化时，
先使用 [`frontend-design`](../frontend-design/SKILL.md) 确定视觉方向，再回到本 Skill
落实项目技术基线、组件复用、可访问性和验证要求。

使用 `frontend-design` 时：

- 只复用其设计方法和视觉决策，不照搬其他项目的 Vue 3 API、组件名或依赖。
- 视觉创意必须服从本项目已有组件库、样式体系、可访问性和性能边界。
- 普通业务页面、表单、表格不需要为了“美化”强制引入新视觉语言；优先复用现有样式。

## 修改前检查

1. 阅读仓库 `AGENTS.md`，遵守其中的流程、安全、OpenSpec 和运行验证约束。
2. 先检查已有前端目录、组件、样式、API 客户端、路由和状态模块，再决定是否新增模式。
3. 以仓库指导和构建配置为准确认技术基线：Vue 2.7.16、TypeScript、Vite、Element UI 2.0.0。
   未明确完成迁移前，禁止引入 Vue 3 专属 API，例如 `<script setup>`、`defineModel`、
   `defineProps`。
4. 优先使用项目已有组件和样式体系。已有同类组件时必须复用；修改公共组件前评估所有调用方，
   尽量保持向后兼容。

## 注释规范

- 🔴 每个新增或修改的代码文件必须有总体中文注释，说明文件职责、所属页面/模块和必要的交互或数据边界。
- 🔴 每个新增或修改的方法、函数、计算属性和事件处理器必须有简要中文注释，说明用途、关键入参/出参和重要副作用；
  简单的模板表达式或明显的声明式配置可遵循项目既有约定，但复杂逻辑仍必须补充说明。
- 🟡 注释应说明界面行为、业务意图和限制条件，不逐行翻译代码；实现或交互变化时同步更新注释。
- 🟡 公共组件、组合逻辑、API 方法、路由守卫和状态操作的注释应优先完整，避免只写“处理数据”“初始化”等无效描述。

## 组件与页面

- 页面负责组合和用户流程；只有存在稳定复用场景时才提取公共组件或工具函数。
- 明确 props、事件、默认值、加载状态和错误状态；禁止直接修改 props 或无意暴露可变内部状态。
- `v-for` 使用稳定的业务标识作为 key；列表可能新增、删除、排序或分页时禁止使用数组下标。
- 弹窗、表单、表格和详情组件遵循现有交互模式；已有项目组件能满足需求时，不用原生标签重造基础控件。
- 新页面和弹窗必须有可发现的路由、权限边界，以及可用的空数据、加载中和失败状态。

## TypeScript 与数据流

- 为 API 参数、响应、视图模型、枚举和事件定义明确的 interface/type；避免 `any`，不可信数据使用 `unknown`
  并在使用前完成类型收窄。
- API 请求集中在项目约定的 API/service 层，不在模板中请求，也不在多个组件中散落 URL。
- 在数据边界声明请求和响应类型；后端数据只在一个明确位置完成规范化，避免模板中重复转换。
- 默认使用局部状态；只有多个页面或相互独立组件确实共享生命周期时，才提升到共享状态。
- 显式处理加载、空数据、失败、重试和过期响应；避免重复提交以及旧请求覆盖较新操作结果。

## 表单、表格与交互

- 提交前校验必填项、格式、范围和跨字段规则；服务端校验仍是最终权威。
- 修改操作进行中应禁用或保护提交入口；成功和失败都要给出清晰结果，不暴露内部异常细节。
- 表格明确行标识、分页、排序、筛选、选择和空状态，区分服务端分页与前端分页。
- 删除等破坏性操作必须二次确认，并具备失败后的安全处理路径；不能仅根据 HTTP 成功就假设业务操作完成。
- 用户可见文案遵循项目统一语言和术语，禁止添加过小的提示文字或只有英文的提示，保持标签清晰可读。

## 样式与可访问性

- 复用已有设计变量、组件样式、布局工具、间距、颜色和响应式规则，不为单个页面引入互相竞争的视觉体系。
- 页面专属样式应在框架支持时使用作用域，选择器保持局部，避免全局覆盖影响其他页面。
- 禁止在前端代码硬编码密钥、环境地址或用户专属数据；使用项目配置和 API 抽象。
- 保证键盘可操作、焦点可见、表单有明确标签、弹窗有可访问名称、阅读顺序合理；重要错误不能只输出到控制台。
- 不仅依赖颜色表达状态；除非内容已明确清洗，禁止使用 `v-html` 渲染不可信数据。

## 业务工作台页面视觉规范

适用于业务处理向导、任务列表、业务场景 Skill、大模型配置及后续同类管理入口。视觉目标是让管理员在页面切换时始终看到一致的“标题—操作—内容”层级；优先在 `frontend/src/styles/index.css` 提取稳定的公共布局，再在页面内保留少量作用域样式。

### 页面层级

1. 页面标题只保留核心业务名称，例如“任务列表”“业务场景 Skill”“大模型配置”；不得在标题附近重复同义副标题或堆叠说明文案。
2. 列表和管理页标题后直接展示操作区和内容卡片，不添加重复业务名称、状态、数量或页码的总览卡片；记录数量保留在表格工具栏或记录标题中即可。
3. 操作区紧邻内容卡片：查询字段位于表格外部；查询、重置、新建等同一业务动作放入同一操作组；没有实际信息增量时，不添加“筛选与操作”等副标题。
4. 表格、表单和工作区使用统一的暖白圆角、边框和阴影节奏。新增、编辑弹窗复用 `workbench-dialog` 与 `workbench-dialog-form` 的标题区、表单间距和底部操作区；表格继续复用 `standard-table-panel`、`standard-data-table` 与 Element UI，不为视觉效果重造表格组件。
5. 两步向导等流程页保留步骤、表单和确认逻辑，但其主卡片、侧栏业务概况和操作按钮应使用同一暖白卡片边界与橙色强调色，不得为了统一外观破坏流程顺序。
6. 桌面端工作台侧栏保持完整视口高度；菜单超出视口时在侧栏内滚动，不随右侧页面内容高度缩短。

### 密度、分页与响应式

- 任务列表默认每页 10 条，分页器提供 10、20、50、100 条切换；切换页大小后回到第一页，并继续使用服务端分页。
- 信息区保持紧凑，优先减少冗余标题和间距，不以缩小用户可读文字或隐藏必要标签换取空间。
- 窄屏下操作栏纵向排列；输入框和按钮可换行，但表格仍通过既有横向滚动容器保持字段可读。
- 橙色强调仅用于层级和焦点，不用于单独表达业务状态；状态仍须使用中文文本、标签或图标辅助说明。

### 颜色与样式边界

- 延续工作台的暖中性色卡片体系：暖白内容面、浅灰米色边框、低对比阴影和克制的橙色强调；禁止引入紫色渐变、荧光大色块或与侧栏冲突的独立主题。
- 公共入口页样式使用明确前缀（例如 `entry-`），不得通过泛化元素选择器覆盖其他页面；页面确有独特布局时使用 `scoped` 样式补充。
- 视觉变化必须服务于任务、配置和审计操作。没有业务含义的装饰性动效、纹理或说明文字不应进入管理工作台。

## 路由、权限与安全

- 按项目路由结构注册页面，遵循既有懒加载和路由元信息约定。
- 前端权限用于改善可见性和操作体验，后端权限才是安全边界；隐藏按钮不等于授权。
- 路由参数、查询参数、上传文件和 API 响应都视为不可信输入，必须通过框架安全机制渲染和处理。
- 除非项目安全设计明确要求，避免把 Token 或敏感信息存入浏览器持久化存储。

## 验证

根据改动风险运行相关类型检查、Lint/格式检查、单元或组件测试和生产构建。涉及路由、权限、API、表单或表格时，
至少验证正常、加载中、空数据、失败、重复提交和未授权场景。

如果当前环境未启动，按照 `AGENTS.md` 将运行和人工验证留给用户，并明确说明未验证范围及风险。

## 评审清单

- 是否优先复用了已有组件、API 客户端、样式变量、路由或状态？
- 代码是否符合 Vue 2.7.16、TypeScript 和 Vite 基线？
- props、事件、类型、请求状态、权限和失败路径是否明确？
- 用户文案是否清晰统一，没有英文-only 或过小提示？
- 样式是否局部、可访问，并与现有设计体系兼容？
- 管理入口是否遵循“标题—操作—内容”层级，且没有重复副标题、总览卡片或脱离表格的无关操作？
- 任务列表是否保持每页 10 条默认分页及既有服务端筛选、分页边界？
- 类型检查、测试和构建是否与改动风险相匹配？
