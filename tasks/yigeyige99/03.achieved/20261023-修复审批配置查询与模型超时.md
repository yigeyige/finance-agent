## 需求

### ID&标题

修复业务处理 guidance 审批配置查询准确性与前端模型调用超时

### 描述

对「新建业务处理 → 开始模型分析」全链路验证时发现两个问题，需要修复：

1. 模型查询 `basedata.t_audit_configuration` 审批配置时漏查：模型用数字 USERID（如 `21615284`）和系统角色名去匹配 `EMP_IDS`/`ROLE_CODE`，但该表 `EMP_IDS` 实际存的是人员登录账号 USERCODE（如 `ZENGLINGRUI`）、`ROLE_CODE` 存的是审批环节角色（如 `ZCGLY`），导致返回 0 行，结论与真实 EMS 数据不符。
2. 模型分析总耗时超过前端 `MODEL_TIMEOUT`（240s），页面报「网络暂时不可用」，但后端实际能完成，链路被前端超时截断。

## 背景

2026-10-23 用 Playwright + 免密身份（`X-Test-Identity: platform-admin`）从业务场景 Skill「审批流程处理」发起新建业务处理（对象 ZENGLINGRUI），验证到：

- 任务创建、Skill 关联持久化（`task.task_business_scene_skill`）、Skill 加载进模型上下文、agent 自动分析 EMS 数据库（3 轮查询）均正常。
- 但 agent 第三轮查 `t_audit_configuration` 返回 0 行；真实 EMS 中曾令睿在该表有 15 条「资产管理员（ZCGLY）」审批配置，根因是查询条件用错字段语义。
- guidance 同步接口耗时 > 300s，前端 240s 超时后报「网络暂时不可用」。

## 目标

- [x] 修正模型查询提示词，明确 `t_audit_configuration.EMP_IDS` 存 USERCODE、`EMP_NAMES` 存姓名，查询审批配置时用 USERCODE 或姓名匹配，不用数字 USERID。
- [x] 提高前端模型调用超时，覆盖后端完整 guidance 耗时，避免链路被前端超时截断。

## 验收标准

- 后端 `DeepSeekBusinessModelClient` 选表与查询规划提示词包含 `t_audit_configuration` 字段语义说明。
- 前端 `model-api.ts` 模型调用超时大于后端实际 guidance 耗时上限。
- 重新触发 guidance 后，`t_audit_configuration` 证据不再是 0 行（能查到 ZENGLINGRUI 的审批配置），且页面不再报「网络暂时不可用」。
