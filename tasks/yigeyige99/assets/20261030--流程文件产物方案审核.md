# 流程文件产物方案审核

审核日期：2026-10-30
范围：`20261030- 流程文件产物生成.md`、`openspec/changes/generate-process-artifacts/` 四件套、V29 场景调查与决策包提示词，以及现有调查、决策包调用链。此次仅审核，未修改方案或实现。

## 结论

**建议修改方案后再实施。**“调查 → 决策包 → 文件”分步、文件独立触发、失败保留旧产物是合理的最小闭环；但当前切片只定义了最后一步，前两步传递给文件生成的业务信息不够，且“可导入 EMS”的验收缺少导入契约证据。单次模型上下文不超过 1M 是上限，不要求先引入分块或复杂编排；仍须按实际模型上限和每次构造的输入计量。

## 必须先修正的问题

### 1. 决策包不能稳定承接模糊初稿或用户附件

V29 调查提示词要求提炼节点、分支、金额和变量；现有调查调用可接收用户附件及场景样例附件正文，也会保存数据库证据。但决策包调用目前只固定任务标题、原始问题、数据库证据和决策包提示词；未带调查草稿、用户附件内容或场景样例正文。文件生成设计又只带任务信息、决策包文字方案和生成提示词。若关键流程细节只在附件或调查草稿中，后两次模型调用会丢失。参考：`BusinessModelInteractionService.java:132-157`、`BusinessDecisionPacketService.java:79-89`、`design.md:56`。

**最小修正**：先明确“可生成文件的权威业务输入”是什么，并贯通到决策包和文件生成。可复用现有调查草稿的受限字段与必要附件投影，不必增加新调查状态机。对缺少节点、角色、分支条件、金额边界等必填事实的输入，返回需补充项，不能用样例代填。决策包保存时明确其对应的任务输入和调查结果；文件生成读取该次固定结果，避免只凭一段概述重建流程。

### 2. 中间表示与 EMS 文件之间仍有未定义的业务映射

设计中的示例只有节点、连线、分档、单个部门模板。它未说明审批规则的 `processId` 如何同部门模板 `processTemplateCode`、BPMN `process_id` 关联；节点变量的 `procdefId` 取值来源；`rules` 与流转条件如何引用同一个金额档位；条件表达式中的变量是否存在；以及多部门审批规则如何表达。仅校验 id 唯一、引用存在、枚举合法和 `min < max`，不足以保证四份文件彼此一致。样例实际含 48 行节点变量、13 个 BPMN 用户任务和 30 条流转，不能简单按“每个节点展开固定变量行”推定。参考：`design.md:19-52`、V29 四个附件正文。

**最小修正**：先用一个真实目标流程列出中间表示字段到四种文件关键字段的映射表，标记“业务输入 / 模板常量 / 本次生成的共享标识 / EMS 导入时分配”。只实现该流程需要的节点和分支形态。校验共享标识、节点引用、条件变量、金额档位和文件间引用的一致性。尚未确定的 EMS 字段不要自行猜值。

### 3. “可导入”不能由样例结构相似或编译通过证明

V29 最后一个样例名为 `BPMN.xml`、声明 `text/xml`，正文却是编辑器 JSON。当前设计称产物为“BPMN 定义”，尚未明确下载文件名、媒体类型、编码及 EMS 实际导入口接受的是编辑器 JSON、XML，还是另有包装。静态样例也不能证明新增流程的业务标识、字段默认值及导入顺序有效。参考：`V29__approval_process_generation_scene.sql:14,185`、`design.md:7,48-52`、任务验收标准。

**最小修正**：核对 EMS 导入入口或导出实现，固定四种文件的格式、文件名与依赖顺序。自动检查 JSON 结构和跨文件引用；最终“可导入并可在 EMS 打开”作为用户手工验收项。当前项目约定由用户启动环境并手动验证，不能把静态检查写成导入成功的证据。

## V29 提示词审核

### 调查提示词

- 方向正确：先提炼业务，再按需查询 EMS，参考四个样例。
- “生成 4 个文件”写成固定目标，和切片的 2～4 个条件产物矛盾。应按业务需要判定规则和部门模板是否适用，并说明理由。
- 只要求输出节点清单等，未要求逐项标明“用户已给出 / 附件提取 / 数据库佐证 / 尚缺失”。对于不清晰输入，容易把样例流程误当目标流程。应要求列出待确认的关键事实，并禁止复制样例中的公司、角色、金额、流程标识作为新流程事实。
- 关键表列表可作调查线索，不应预设表和字段在目标实例中都存在。拟补 `sys_value_set` 时同样应先确认实际 schema、字段和值集含义，再使用查询结果。
- 当前 V28 的通用提示词已有按需请求场景附件机制，但最多请求 2 个正文；四个样例不会在同一轮全部进入模型。应明确调查阶段只读与当前问题相关的样例，文件转换阶段由代码中的模板或受控样例提供精确格式。

### 决策包提示词

- 五字段与现有 `BusinessPacketAnalysisSuggestion` 契约一致，可沿用；“生成方式另行确定”与本切片已选方案不一致，应删除或改为“此阶段不输出文件正文”。
- 当前 `recommendedGoal`、`reason` 等单字段上限为 2000 字符。若仍让它承载完整节点图、条件和参数，容易截断或泛化；决策包应明确选定方案、关键流程边界和未决项，详细结构应来自固定的调查结果，不能假设五字段文字足以复原四份文件。
- 加一句约束：证据不足时明确缺失项，不宣称“流程整体合理”或“可导入”；备选方案不参与文件生成，除非用户明确选择。现有实现生成即完成，没有独立“确认”状态，任务文档的“决策包确认后”应改成“已有最新决策包”或明确新增确认动作。

## OpenSpec 切片收敛建议

1. 把“调查结果到决策包、再到文件”的输入来源与缺失信息处理写进 `design.md` 和可验收场景。当前“调查与决策包链路不变”的断言只有在已确认细节能完整传递时才成立。
2. V30 先放场景提示词、产物存储与本场景必要提示词修订。`GUIDE_HANDLING` 通用模板调优如确属本闭环必需，应写明对应验收；否则拆出本切片，避免改动所有场景。
3. `proposal.md` 宣称修改了 `business-scene-skill-attachment` 能力，但 delta spec 只有 `business-process-artifact`。补齐提示词维护的规格，或把它纳入新能力，不要仅在设计中描述。
4. 产物与决策包修订的关联需定一个最小规则：保存来源 `packetId/revision`，重新生成后旧文件继续下载还是标记过期。当前只按 task 覆盖，会使任务再次生成决策包后，旧文件看起来仍对应最新决策包。
5. 将验收从“2～4 个文件都可导入”细化成一个受限样例：确定目标流程、必需文件、关键跨文件字段、静态结构检查，以及用户手工导入结果。生成失败时事务保留旧产物的场景已有定义，继续保留。

## 建议的最小实施顺序

1. 固定一个目标流程和 EMS 导入契约，整理四种文件的字段映射与共享标识。
2. 修订调查/决策包提示词，打通必要业务事实的传递；不引入新的治理机制。
3. 定义仅覆盖该目标流程的中间表示和转换器，产物绑定决策包修订；失败保留旧文件。
4. 做静态转换验证与前后端编译；由用户启动本地环境，手工验证 EMS 导入。

## 需要业务确认的三点

1. 首版是否只支持一个确定的目标流程形态，遇到会签、并行等超出样例的形态明确拒绝？
2. 文件生成所依据的是“最新生成的决策包”，还是必须由用户明确确认某个修订？
3. EMS 实际导入入口是否已经确认接受 V29 所示四种正文，尤其是名为 `.xml` 但正文为 JSON 的最后一份？

## 审核后的方案修订记录（2026-10-30）

上述审核结论针对修订前的任务与 OpenSpec。随后与用户逐项确认并修订规划文件，关键调整为：调查结论及证据在点击生成决策包时固定入包，文件仅从该包生成；首版限本场景及五类节点、顺序/排他流转；流程模型必生成，其余配置按适用性生成，用户可选择打入 ZIP；EMS 现有 ZIP 导入会自动部署和设置运行版本，用户接受该行为；允许部分流程和空值，但不满足最低导入要求时只能标待修复；文件保留最新及上一次两批。此前“决策包后只凭文字方案生成文件”“重复生成覆盖全部旧产物”“BPMN 与节点参数必生成”的批评或描述已由新规划替代。

静态核查 EMS 导入实现：`PscActReModelPrvService.importZipProcessZip` 遍历 ZIP 内容，先处理文件名含 `.xml` 的编辑器 JSON 模型，再处理可选配置；未检查必须有四个文件，但模型导入会立即部署和设置运行版本。审批规则导入按 JSON 数组读取，而 V29 样例为单对象，应以导入契约为准。以上是源码判断，实际导入仍待用户手工验证。

## 四文件 ZIP 导入标识与复用规则补充核查（2026-10-31）

核查对象为 `docs/测试流程.zip` 及其解压后的四个文件，并对照 `ems-process/ems-process-provider/src/main/java/cn/com/crc/ems/process/model/PscActReModelPrvService.java:247-405`、`PrcoSetActivitiUtil.java:147-176` 和 EMS Admin 的审批规则保存逻辑。当前 ZIP 的四个条目均在根目录、带 UTF-8 文件名标记；Java 可以读取。以下结论只对应这条 `/psc/actmodel/pscActReModel/importZip` 导入链路，不代表实际服务端上传与业务部署已经验收。

### 全新流程的标识传递

```text
K = appid + "-" + 新 UUID（导入时生成的流程模板 key）
模型 properties.process_id = K
部门审批流 processTemplateCode = K
审批规则 head.processId = K

D = 模型部署成功后返回的流程定义版本 ID
节点参数配置 procdefId = D

N = ZIP 文件名去掉 .zip 后的名称
M = 流程模型文件名去掉 BPMN.xml 后的名称
模型请求及流程模板名称 = M
部门审批流 processTemplate = N
审批规则 head.processName = N
```

导入方法忽略上传参数 `procSetName` 的值：部门审批流与审批规则名称取 ZIP 文件名，模型及流程模板名称取 `*BPMN.xml` 文件名。模型画布内部的 `properties.name` 也不会自动改写。当前三个名称均为“测试流程”；若新流程改名，应让 ZIP 文件名、模型文件名、画布名称及节点显示名称保持一致。部署没有得到 `D` 时，当前代码仍可能继续处理后续配置，不能把静态字段映射视为部署成功证明。

| 文件 / 字段 | 全新流程的建议 | 导入代码实际行为 |
| --- | --- | --- |
| 流程模型 `properties.process_id` | 使用新流程的 K；文件内旧值只作占位 | 强制覆盖为新生成的 K |
| 流程模型根 `resourceId` | 使用当前模型画布标识 | 强制覆盖为 `canvas` |
| 模型 ID、流程模板记录 ID、部署版本 ID | 必须为新记录 / 新版本 | 由模型服务、持久化和部署产生，不使用文件中的旧 ID |
| 部门审批流 `id`、`processTemplateCode` | `id` 留空由目标库生成；编码必须是 K | 当前样例未带 `id`；编码覆盖为 K |
| 节点参数配置 `id`、`procdefId` | `id` 留空由目标库生成；版本 ID 必须是 D | 当前 48 行的 `id` 均为空；`procdefId` 全部覆盖为 D |
| 审批规则 `rulesHeadId`、各行 `rulesLineId` / `rulesHeadId`、`head.processId` | 主键和行头关联均用新值；流程 ID 必须是 K | 旧规则 ID 全部置空，`processId` 覆盖为 K；保存端生成新主键并连接行头 |
| 模型请求及流程模板名称 | 应为新流程名称 M，名称不是唯一 ID | 由 `*BPMN.xml` 文件名推导；画布内 `properties.name` 不会自动同步 |
| 部门审批流 `processTemplate`、审批规则 `head.processName` | 应为新流程名称 N，名称不是唯一 ID | 由 ZIP 文件名覆盖；文件内旧名称不生效 |

生成文件时无需预先编造 K、D 或数据库主键，但应保留导入解析需要的字段结构。导入代码对这些值执行覆盖或置空；不同文件中由目标系统分配的 ID 不能提前硬编码成同一个旧流程的值。

### 可复用但须保持引用一致的字段

- 模型子节点的 `resourceId`、`overrideid`，以及连线的 `outgoing` / `target.resourceId` 是图内引用。整体复制同一张图可以保留；若重新生成节点 ID，须同步重写图内所有引用。`overrideid` 在新流程内应唯一，并与外部节点配置所引用的活动 ID 对应。
- 节点参数的 `actId` 和部门审批流的 `approvalNode` 仅在对应节点仍存在且业务含义相同时保留。当前部门审批流的 `approvalNode=act_11` 能在模型中找到；导入代码不会修正其他失效节点引用。
- 节点参数的 `variableName`、`variableValue`、取人方式等；部门审批流的业务线、组织、公司、角色和取值规则；审批规则的 `workflowLineKey`、`workflowLineValue`、金额和币种，均为业务配置。只有目标流程确实沿用同一业务规则时才能复用，不能因为导入代码接受该字段就直接复制样例值。
- 上传参数 `categoryId` 可以选择已有且适用的流程分类，不需要为每个新流程生成新分类 ID；`sort`、`remarks` 按本次流程填写或使用接口默认值。
- 节点参数和部门审批流中的 `createdBy` / `updatedBy` 等来源账号没有被导入方法统一改写；跨环境时需按目标环境处理。审批规则头的 `createdBy` 由 EMS Admin 保存服务改写为当前用户，不能假定四类文件的审计字段规则相同。

### 当前样例需要额外核对的节点参数

`节点参数配置.json` 有 48 行，涉及 24 个不同的 `actId`；其中 15 个 ID 在当前 `测试流程BPMN.xml` 的编辑器 JSON 中完全找不到：`NCC_010`、`NCC_020`、`act_050`、`act_090`、`act_12`、`act_14`、`act_140`、`act_170`、`act_180`、`act_190`、`act_200`、`act_201`、`act_210`、`act_301`、`act_302`。导入代码只替换这些行的 `procdefId`，不会验证或修正 `actId`。因此它们可能被保存，却无法作用于新流程中的节点。首版最小产物应只保留实际节点需要的配置，并静态校验 `actId` 与模型节点一致；最终效果仍由用户手工导入验证。
