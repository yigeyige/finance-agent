# 后端编码规范

本文档是本项目后端开发的通用约束。项目代码尚未形成稳定的历史实现时，以本文档和当前 `AGENTS.md` 为准；后续若形成模块级约定，应在不违反本规范核心原则的前提下补充到对应模块文档。

## 核心原则

1. **先明确边界，再实现代码**：先确认业务对象、输入输出、权限边界、数据来源和失败行为，再选择类、接口和依赖。
2. **单一职责、最小改动**：Controller 负责协议适配，Service 负责业务编排，Repository/Mapper 负责数据访问；避免把业务逻辑堆进“上帝类”。
3. **可验证、可追溯**：关键业务结果应能通过测试、日志、审计或数据记录复核；时间、版本、来源和状态变化不得依赖隐式约定。
4. **默认安全失败**：输入校验、权限检查、敏感信息保护、超时、重试和幂等必须显式设计；不得为了“方便调用”放宽边界。
5. **复用优先**：优先使用项目已有抽象、框架能力和成熟工具类；新增公共组件前先检索是否已有等价能力。
6. **兼容性优先于炫技**：只使用技术基线支持的 API；升级依赖必须有明确收益、影响分析和验证记录。

## 规范等级

| 等级 | 标记 | 含义 |
| --- | --- | --- |
| 强制 | 🔴 | 必须遵守；违反可能导致安全、数据一致性或运行事故。 |
| 推荐 | 🟡 | 默认遵守；确需偏离时应在代码或变更说明中解释原因。 |
| 参考 | 🟢 | 特定场景下采用，不作为普遍门禁。 |

若本规范与更高优先级的用户需求、框架官方约束或已确认的模块契约冲突，应先记录冲突并明确采用的规则，不可静默选择。

## 技术基线

| 技术 | 基线 | 使用约束 |
| --- | --- | --- |
| Java | 17 | 使用显式、可读的 Java 17 写法；禁止引入高于基线的语言或 JDK API。 |
| Spring Boot | 4.0.4 | 按项目依赖管理使用 Spring Boot 4 及其配套 API。 |
| Spring Framework | 7.0.7 | 优先使用项目统一配置和生命周期机制。 |
| AgentScope Java | 2.0.3 BOM | Agent 能力通过已批准的适配层接入，业务代码不得绕过边界直接散落调用。 |
| PostgreSQL JDBC | 42.7.11 | 数据库访问遵循 PostgreSQL 方言、事务和参数化要求。 |
| pgvector Java SDK | 0.1.6 | 向量能力封装在明确的基础设施或领域适配层中。 |

依赖版本以构建文件和依赖管理为最终准据；本文档中的版本用于防止误用新版本接口，不替代构建配置。

## 分层与依赖方向

建议采用以下边界：

```text
接口层 Controller / API DTO
        ↓
应用层 Application Service / 用例编排
        ↓
领域层 Domain Model / 领域服务 / 业务规则
        ↓
基础设施层 Repository / Client / Agent Adapter
```

- 🔴 Controller 不直接访问数据库、调用外部系统或承载复杂业务判断。
- 🔴 Service 不返回持久化 Entity 作为公开 API 契约；使用 DTO、VO 或明确的领域结果对象。
- 🔴 基础设施实现不得反向依赖接口层；外部系统调用必须经过可替换的接口或适配器。
- 🟡 类和方法应围绕业务能力命名，避免 `Util`、`Manager`、`Helper` 等无法表达职责的泛化命名。
- 🟡 公共抽象应在出现至少两个稳定使用场景后提取，避免过早框架化。

## 接口、校验与错误处理

- 🔴 请求参数在接口边界校验；业务层再次校验关键不变量，不信任前端或上游已校验。
- 🔴 API 响应结构、错误码和分页字段保持项目统一，不在单个 Controller 私自发明响应格式。
- 🔴 异常不得被空 catch、日志后吞掉或用 `null` 静默替代；无法处理时保留根因并交给统一异常处理器。
- 🟡 对可预期业务失败使用明确的业务异常/错误码；系统异常记录堆栈但不向外暴露密钥、SQL、内部路径或原始提示。
- 🟡 修改、重试、消息消费和外部副作用操作要设计幂等键或去重策略。

## 数据访问与事务

- 🔴 所有 SQL 使用参数绑定，禁止拼接用户输入；写操作必须明确事务边界。
- 🔴 事务范围围绕一个完整业务用例设计，避免在事务中执行不可控的长耗时网络调用。
- 🔴 分页、排序、过滤字段必须经过白名单或框架安全封装；禁止直接接收任意 SQL 片段。
- 🟡 数据库字段、枚举、时间和金额的 Java 类型要与业务语义一致；金额禁止使用 `float`/`double` 作为持久化或计算主类型。
- 🟡 数据库迁移必须可重复检查、可回滚或有明确补偿方案，并同步更新必要的模型、索引和验证。

## 日志、配置与安全

- 🔴 使用项目统一日志门面和参数占位符，禁止 `System.out`、字符串拼接日志和无上下文异常日志。
- 🔴 日志不得记录密码、Token、密钥、完整身份证件号、完整账号或真实敏感业务数据；必要时脱敏或记录摘要。
- 🔴 配置、密钥和连接串通过配置注入或密钥管理提供，禁止硬编码和提交 `.env`、凭据文件。
- 🟡 关键操作日志包含 request/correlation id、业务对象标识、结果和耗时；不要用日志替代审计记录。
- 🟡 超时、重试、熔断、连接池和线程池参数应集中配置，并说明默认值和边界。

## 通用操作和工具类选择

优先复用项目已引入且版本稳定的工具，避免重复造轮子。选择顺序为：项目已有公共组件 → Apache Commons 等成熟库 → JDK 17 标准库 → 其他新增依赖。新增依赖必须说明必要性和维护成本。

| 场景 | 推荐做法 |
| --- | --- |
| 字符串/集合判空 | 明确区分 empty 与 blank；优先项目统一工具，不混用语义相同但行为不同的工具类。 |
| 日期时间 | 使用 `java.time`（如 `Instant`、`LocalDate`、`OffsetDateTime`），统一时区和序列化格式，禁止新代码使用 `SimpleDateFormat`。 |
| 文件与流 | 使用 JDK NIO 或项目统一 IO 工具；确保流关闭、路径校验和临时文件清理。 |
| 编码/摘要 | 使用 JDK 或 Apache Commons 的成熟实现；密码存储使用专用密码哈希，禁止自定义“加盐+MD5”。 |
| JSON | 使用项目统一 JSON 序列化配置，避免同一模块混用多个库或手写 JSON 字符串。 |
| 对象转换 | 跨层 DTO/VO 转换优先使用显式映射或项目统一映射工具；重要字段不要依赖不可见的反射复制。 |
| 反射 | 仅在框架适配或明确必要时使用，限制访问范围并补充测试；业务主流程优先显式代码。 |
| 并发/缓存 | 优先使用 Spring/JDK 并发抽象；缓存必须定义 key、TTL、一致性和失效策略，分布式锁必须有超时和 finally 释放。 |

工具类选择不能掩盖错误语义。例如 `isEmpty` 不等于 `isBlank`，日期“本地时间”也不等于带时区的时间点；调用前应按业务含义选择。

## 测试与验证

- 🔴 新增业务逻辑必须有与风险匹配的测试，至少覆盖正常路径、边界条件、失败路径和权限/数据隔离路径。
- 🔴 修改接口、数据库或消息契约时，补充契约、集成或迁移验证；不能只依赖编译通过。
- 🟡 测试数据隔离，外部依赖可控替身；测试名称描述行为和条件，避免依赖执行顺序。
- 🟡 提交前至少完成格式/静态检查、编译和相关测试；无法运行时记录原因、未覆盖范围和剩余风险。

## 代码评审红线

- 禁止提交密钥、账号密码、生产连接串和真实用户数据。
- 禁止未经确认执行删库、批量删改数据、重置分支或覆盖用户文件。
- 禁止为了通过测试关闭校验、吞异常、扩大权限或跳过审计。
- 禁止引入与现有技术基线不兼容的依赖、API 或配置格式。
