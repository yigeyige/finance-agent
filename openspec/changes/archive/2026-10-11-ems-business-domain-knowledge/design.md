## Context

本地 EMS 简易版已通过 DBX 完成首轮结构核查：可识别业务库、表、字段、注释和少量外键，但当前无业务样本，不能将结构推断表述为已验证的业务规则。现有知识以 Markdown 保存，工作台没有统一入口；现有前端已具备身份驱动侧栏、受保护路由、统一管理页样式和集中 API 客户端。

本次只展示用户明确保留的业务域，排除 `claim`、`xxljob`、`arch_db`。页面和接口均不得访问 EMS 数据库、返回实际业务数据，或暴露数据库连接细节。

## Goals / Non-Goals

**Goals:**

- 向具备工作台读取权限的用户提供一份内置、只读、版本化的 EMS 业务域知识目录。
- 复用现有身份守卫、REST 响应模式、Vue 2 路由和工作台页面样式。
- 明确每条知识的结构核实边界，避免把空库结构解释成真实业务事实。
- 让知识文档和工作台展示使用同一组受控内容。

**Non-Goals:**

- 不连接、不查询、不写 EMS 数据库；不接入 DBX 作为运行时能力。
- 不包含 `claim`、`xxljob`、`arch_db`，也不展示真实人员、账号、单据、金额、脚本、连接信息或完整数据库元数据。
- 不提供知识编辑、导入、搜索、模型问答或流程/审批配置变更能力。
- 不确认跨库业务关系、状态码语义和权威来源；这些需后续授权样本或代码证据补充。

## Decisions

### 内置目录经后端只读 API 提供

后端在独立 `emsknowledge` 模块中维护小型不可变目录，并通过受权限保护的只读端点返回 DTO。目录由代码控制、启动即可使用，不引入迁移或额外依赖。

选择该方案而非读取 Markdown：Markdown 缺少稳定 API 结构，前端解析会把文档格式变成运行时契约。选择该方案而非新建持久化表：本次目录由已经核实的静态结构组成，尚无管理员在线维护需求，持久化会带来不必要的写权限、迁移和生命周期复杂度。

### 以业务域为最小展示单元

每个域返回固定字段：代码、名称、用途、所属库、表数量、关键表、可信边界和核实提示。前端使用域卡片和关键表折叠详情展示，不展示未被目录明确列出的表或字段。

选择领域级目录而非全库表浏览器：当前 EMS 有 1158 张表，且部分表涉及敏感数据。领域级目录能支持场景定位，同时保留后续按授权扩充表级知识的空间。

### 读取权限沿用 `TASK_READ`

知识域属于工作台的只读分析辅助能力，前后端均要求现有 `TASK_READ` 权限。后端仍执行权限校验，前端菜单可见性和路由守卫只改善体验，不构成安全边界。

### 知识可信边界显式返回

后端返回固定中文边界说明：目录为“结构已核实”，业务关系、状态枚举和权威来源“待样本或代码确认”。前端在页面顶部和每个域中展示该信息，不让用户误把资料当作实时 EMS 数据。

## Risks / Trade-offs

- [目录与 Markdown 漂移] → 以同一受控目录内容更新文档和 API，并用单元测试固定排除库和关键域。
- [静态表数过期] → 表数仅标注为首轮结构快照；后续刷新知识版本时同步更新。
- [知识泄露配置细节] → 仅输出已批准的业务域、库名、关键表名和概述；拒绝返回连接、任意表结构和真实数据。
- [用户误解可信度] → 统一显示结构核实边界和后续核实提示。
- [菜单膨胀] → 复用现有侧栏内滚动和 `TASK_READ` 可见性，不增加新的权限模型。

## Migration Plan

1. 发布包含静态目录、只读端点、契约和页面的应用版本。
2. 无数据库迁移、无 EMS 数据库操作、无历史数据回填。
3. 回滚时移除该版本代码即可；不会遗留业务数据或外部状态。
