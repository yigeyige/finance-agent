## Context

当前工作台把对象前提和系统对象分别展示，把推荐与备选方案、模型聊天分别呈现；生成后聊天禁用。步骤提议已经进入等待处理状态后，只要尚无执行记录即可安全修改推荐步骤目标。

## Goals / Non-Goals

### Goals

- 保留现有两步任务创建与范围确认路径，减少重复文案和输入。
- 单一“处理对象”字段同时传给前提与范围适配层。
- 仅生成一条推荐步骤；聊天与推荐方案在同一协作区域，生成后仍可请求模型修订。
- 只在任务处于 `WAITING_STEP_APPROVAL`、当前推荐步骤仍为 `PROPOSED` 时更新其目标，并追加审计事件。
- 技术明细显示现有安全元数据；推理强度为可选展示，不传递或保存推理内容。

### Non-Goals

- 不改变已执行、已批准或运行中步骤。
- 不返回模型提示词、推理过程或原始供应商响应。
- 不新增模型供应商字段或推理强度配置。

## Decisions

### 单一处理对象映射

前端移除 `objectKey` 输入及状态，以 `subjectKey` 作为唯一处理对象；范围请求适配时用同一值生成 `objectKey`。模型初稿回填优先使用 `objectKey`，缺失时回退 `subjectKey`。

### 单推荐方案与持续聊天

前端将 `planGoals` 改为单个 `recommendedGoal`，始终以一条 `recommended: true` 提议。对象与范围区域在上，并将处理方式和业务场景等短字段压缩为双列；推荐方案与模型聊天协作区在下，并列展示方案编辑和模型协助，窄屏自动堆叠，形成“确认范围 → 生成初步方案 → 模型修改 → 保存修改”的阅读顺序；模型返回新草稿时，若已经生成步骤，则显示“更新业务方案”按钮并调用受控更新接口。

### 受控更新边界

新增 `PATCH /api/v1/tasks/{taskId}/step-proposals/{stepId}`，请求只有白名单 `goal`。应用服务锁定任务与步骤，验证任务、当前步骤、状态与操作者边界；仅 `WAITING_STEP_APPROVAL` 且 `PROPOSED` 的当前推荐步骤可更新。成功后写审计事件并返回当前步骤视图；其余状态拒绝，不改写历史或执行步骤。

### 技术明细

使用 `ModelCallMetadata` 中已有模型名称、模式、Token 数和耗时。前端把 `reasoningEffort?: string` 视为兼容性可选字段，只有非空时显示；不改动后端当前受控输出。

### 业务场景 Skill 管理

业务场景 Skill 使用独立的 `task.business_scene_skill` 表持久化名称、说明、处理方式和业务场景。目录列表只显示未删除记录；新增与编辑通过受控 REST 接口校验字段后保存，删除记录采用软删除保留操作者和时间审计字段。所有写操作均要求 `OPERATOR` 身份，前端在删除前二次确认并在成功后重新加载列表。

## Risks / Trade-offs

- 一次对象输入不再区分业务前提与系统对象：降低管理员输入成本，但需要模型和管理员确保标识可同时用于两处；当前单系统固定场景下可接受。
- 修改步骤目标不重新生成范围和前提：接口严格限制为未执行的推荐步骤，范围变化仍必须通过既有确认流程重新创建任务。
- Skill 删除后不再出现在目录中，但保留审计记录；当前不将 Skill 自动回填至向导，避免把场景模板与任务范围确认混为一体。

## Validation

- 后端新增推荐步骤更新的正常与拒绝状态测试。
- 前端 `npm run typecheck`、`npm run build`。
- 在 Stub 环境验证创建、生成、聊天修订、更新方案与技术明细显示。
- 验证业务场景 Skill 的新增、编辑、删除与列表刷新。

## Navigation extension

左侧栏保留“新建业务处理”默认入口，并增加“任务列表”和“业务场景 Skill”。任务列表通过只读接口返回当前可信身份发起的最近 50 条任务；业务场景 Skill 以可维护的列表呈现，只暴露业务名称、说明、处理方式和场景，不暴露系统内部字段。

列表页统一采用 Element UI 标准数据表格：白色承载区、浅色表头、清晰列宽、中文状态标签和窄屏横向滚动。任务状态不直接显示内部枚举值；Skill 操作列不使用固定定位，避免中小屏幕产生重复或挤压列。
