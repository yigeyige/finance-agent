## Context

现有 `RetentionScheduleService` 用单线程 `TaskScheduler` 运行固定清理任务，`RetentionJob` 负责互斥和清理日志；管理员页面只能保存时间、读取最近日志。手动触发可能耗时较长，不应阻塞 HTTP 请求。

## Goals / Non-Goals

**Goals:** 平台管理员确认后异步提交一次固定清理任务；防止重复手动排队；复用原清理逻辑、日志和权限，并在页面刷新最新记录。

**Non-Goals:** 不修改到期判定、清理清单、调度配置、任务种类或数据库结构；不在开发过程中真正执行清理。

## Decisions

- 固定 `POST /api/v1/scheduled-jobs/retention-cleanup/runs` 返回 `202 Accepted`；管理员权限由拦截器和 Controller 双重检查。接口不接受任意类名、路径、任务参数。
- 使用现有单线程调度器执行相同的 `Runnable`，单进程原子标记限制同一时间只排队一次手动运行；重复请求返回 `409 Conflict`。定时触发和手动触发串行，手动运行不改动 cron。
- 按钮使用现有 Element UI；用户二次确认后提交。页面显示提交/失败状态，定期读取有界运行日志直到发现新记录；离开页面清理轮询。未保存的时间草稿不会被提交。

## Risks / Trade-offs

- 任务执行可能超过页面轮询窗口：页面保留“已提交”提示，用户可重新进入页面查看结果。
- 应用进程重启会丢失尚未执行的内存队列：接口只表示已接受，不承诺持久队列；现有任务执行日志仍按完成结果写入。
