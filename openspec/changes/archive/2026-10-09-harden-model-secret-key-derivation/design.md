## Context

模型 API Key 以 AES-GCM 密文保存，部署变量提供主密钥。原实现以主密钥的前 32 个 Java 字符转为 UTF-8 字节后构造 AES Key：多字节文本可能超过 32 字节而失败，且后续字符未参与密钥材料。数据库中已存在未加前缀的旧格式密文。

## Goals / Non-Goals

**Goals:**

- 对完整部署主密钥执行 SHA-256，稳定得到 32 字节 AES-256 Key。
- 新写密文使用显式版本前缀，旧密文可继续读取。
- 保持认证加密、随机 nonce 和错误信息不泄密。

**Non-Goals:**

- 不接入外部密钥管理系统、KMS、轮换平台或数据库迁移。
- 不尝试在没有主密钥时恢复旧密文，也不把密钥材料记录到日志。

## Decisions

### 使用 JDK SHA-256 派生固定长度 AES-256 Key

以 UTF-8 编码的完整主密钥输入 `MessageDigest`，输出作为 AES Key。该做法不新增依赖，适合内网配置型部署，并消除字符长度与 AES 字节长度不一致的问题。

### 新密文标记为 `v2:`，旧无前缀密文按遗留规则解密

写入统一产生 `v2:` 前缀。读取检测前缀后选择派生 Key；无前缀密文只走旧规则。这样既防止新写再次使用截断方式，又不强制一次性重写已有数据。

## Risks / Trade-offs

- [旧密文仍依赖旧派生规则] → 仅保留解密兼容，不再产生旧密文；下次编辑 API Key 即自然迁移。
- [主密钥修改导致旧密文无法读取] → 与现有部署语义一致，配置说明明确主密钥需要稳定保管。
- [SHA-256 不是口令 KDF] → 本变更针对已满足最小长度的内网部署主密钥，不把低熵人工口令视为安全密钥来源。

## Migration Plan

无需迁移。发布后读取旧密文仍有效；管理员保存或更新模型 API Key 时会写为 `v2:` 格式。回滚时新格式不可由旧程序读取，因此需要先完成备份并仅在确认未写入新配置时回滚。
