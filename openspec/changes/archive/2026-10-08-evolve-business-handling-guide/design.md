## Context

工作台当前以调查为唯一入口：先创建任务，再分别填写前提对象和范围，范围确认后才允许模型提出步骤，最后还要在页面完成步骤批准。管理员在处理“业务调整”时也被迫使用调查术语，并且无法通过自然语言与模型共同修订结构化方案。

现有任务、范围确认、步骤提议和执行审批的后端边界仍需要保留：范围确认继续是进入后续调查的唯一权威写入；执行 permit 与审批 revision 不暴露到浏览器，也不由模型生成。

## Goals / Non-Goals

**Goals:**

- 用两步向导承接调查和调整：业务说明、模型协作的对象范围与业务方案。
- 在任务创建后，后端仅以任务标题、业务说明、管理员的反馈和可枚举业务选项构造模型输入，返回可校验的结构化草稿。
- 在同一模型交互区保留管理员消息和模型回复，并以最新结构化草稿回填表单与方案列表。
- 管理员可不经过页面批准卡直接写入步骤提议；既有审批 API 和执行安全门保持不变。

**Non-Goals:**

- 不将聊天记录、模型推理过程或未授权字段持久化到任务、审计或浏览器存储。
- 不取消后端执行审批、ExecutionPermit、字段策略或范围确认安全约束。
- 不新增模型供应商、依赖、数据库迁移或跨任务会话记忆。

## Decisions

### 1. 在创建任务后请求受控业务处理初稿

新增 `business-guidance` 模型交互：服务端从任务标题、业务说明和受限的当前表单草稿构造输入，模型严格返回对象依据、范围选择、处理类型、推荐方案、备选方案和简短说明。这样模型可以在范围确认前辅助录入，但不能替代范围确认。

备选方案是只在前端用固定规则推断字段，成本低但无法展示真实模型参与，也无法处理自然语言修订；因此不采用。

### 2. 对话采用“单轮重算 + 前端短暂上下文”

管理员消息和当前结构化草稿随单次请求传递，后端校验长度、可选值和字段形状，再返回模型文本回复与新的完整草稿。前端仅在当前页面保存消息，不保存推理、原始提示词或模型上下文。这样可让管理员直接修改方案，同时避免引入未定义的聊天持久化和审计敏感面。

### 3. 用“生成业务方案”替换页面批准卡

管理员确认模型草稿后，前端顺序保存前提、确认范围、提交步骤提议。页面不再展示批准/拒绝、调用次数或 permit 相关信息；生成后的方案仍以现有步骤提议返回值为权威。后续真实执行仍由既有后端审批能力治理。

直接跳过服务端审批状态并启动 worker 会破坏既有范围/调用上限/permit 边界，因此不采用。

### 4. 视觉采用双栏协作台

保留 Element UI 表单与现有卡片、颜色变量；第二步左侧是可编辑的对象范围表单，右侧是模型消息流与业务方案，窄屏时垂直堆叠。状态通过中文标题、加载文案和模式标签共同表达，而不只依赖颜色。

## Risks / Trade-offs

- [模型初稿不准确] → 初稿始终可编辑，确认范围前强制校验必填字段，模型模式明确可见。
- [聊天输入尝试扩大字段范围] → 后端只接收受限文本、白名单枚举和结构化草稿，范围权限仍由确认接口生成。
- [管理员误以为方案已经执行] → 页面明确写“业务方案已生成”，不把步骤提议描述为已执行，并保留后续证据入口条件。
- [旧任务状态停在待审批] → 本变更不修改既有状态机；工作台将直接展示方案生成结果，真实执行仍由既有受控入口处理。

## Migration Plan

1. 部署后新进入工作台的任务使用两步业务处理向导。
2. 既有任务、范围、步骤和审批记录不迁移；其 REST 契约保持兼容。
3. 如模型交互不可用，保留业务说明与可编辑表单，显示中文失败提示并允许重新请求。
4. 回滚只需回退前后端代码；不会产生新的持久化模型或迁移状态。

## Open Questions

- 当前管理员直接“生成业务方案”仅保存步骤提议；若未来要直接触发执行，需要单独评估并调整执行审批与 permit 安全契约。
