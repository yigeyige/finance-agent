## Context

现有前端在浏览器中使用固定规则生成调查目标，决策包也直接把确定性证据映射为建议。后端已有 `DeepSeekOpenAiAdapter`、思考内容过滤和模型预算配置，但没有 Spring 业务装配或可调用的模型交互用例。当前本地 profile 默认 Stub，`.env.example` 可切换真实 DeepSeek，但 API Key 不进入仓库。

业务人员需要看懂模型何时参与，审计人员需要知道模型模式、模型名称和输入输出摘要，同时不能看到推理过程、密钥或未授权原始数据。

## Goals / Non-Goals

**Goals:**

- 通过后端统一接口完成调查方案生成和证据分析。
- 在真实模式复用 AgentScope DeepSeek 适配器，在 Stub 模式提供明确标识的确定性响应。
- 只发送任务问题、已确认范围和脱敏证据摘要，严格校验 JSON 输出。
- 前端把模型处理与人工审批、人工复核清晰分开。
- 模型失败时保留当前业务输入并安全失败。

**Non-Goals:**

- 本次不让模型直接执行工具、自动审批、自动发布或修改任务范围。
- 不持久化模型思考过程，不新增数据库表，不实现多轮聊天界面。
- 不替换现有确定性证据采集、规则判断和发布重查。

## Decisions

### 1. 增加业务模型端口而不是让 Controller 直接调用 AgentScope

应用层定义方案生成和证据分析端口，基础设施层分别实现 DeepSeek 与 Stub。Spring 配置根据 `finance-agent.deep-seek.stub` 选择唯一实现。这样业务层不依赖供应商 SDK，测试可以使用确定性实现。

### 2. 模型只提供建议，不改变权威状态

模型方案返回推荐目标、备选目标、理由；现有步骤提议 API 仍负责持久化，人工审批仍是执行门槛。模型证据分析返回摘要、风险和建议；现有决策包草稿、复核、发布接口继续作为权威写路径。

### 3. 使用严格 JSON 对象和白名单投影

方案输入仅包含任务标题、问题和已确认范围摘要。证据分析仅包含计数、覆盖状态、事实分类和规则判断陈述，不发送原始业务字段值。响应必须精确匹配预期字段和数量限制；AgentScope 返回的 thinking block 在适配层过滤。

### 4. Stub 必须可见且不可冒充真实模型

响应包含 `mode`、`modelName`、`inputDigest`、`outputDigest`、token 数和耗时。Stub 返回 `STUB` 与“本地模拟模型”，前端用中性标识说明这是流程验证；真实调用返回 `LIVE` 和配置模型名称。

### 5. 前端采用阶段式模型工作台

范围确认后先展示“正在分析问题和范围”，成功后展示模型理由、推荐步骤和备选方案，再进入人工批准。决策包先展示证据概况，业务人员主动触发模型分析，成功后核对模型摘要和建议并确认业务影响。

## Risks / Trade-offs

- [真实模型延迟或限流] → 15 秒前端超时、后端单次调用超时和无自动重试；保留重试按钮。
- [模型输出格式错误] → 严格 JSON 校验，失败时不保存步骤、不生成决策包。
- [Stub 被误认为真实能力] → 响应和页面持续显示“本地模拟模型”。
- [敏感数据进入模型] → 后端自行加载并投影脱敏摘要，不接受前端传入任意证据 JSON。
- [模型建议不可靠] → 所有模型产出均标为建议，必须经过人工审批或复核才能进入后续权威状态。

## Migration Plan

1. 部署兼容的后端模型 API；Stub 为本地默认模式。
2. 部署前端阶段式交互；旧任务仍可按当前证据继续进入决策包。
3. 配置 `FINANCE_AGENT_DEEPSEEK_STUB=false` 与运行环境密钥后启用真实模型。
4. 回滚时恢复旧前端，新增 API 无数据库迁移，可直接停止使用。
