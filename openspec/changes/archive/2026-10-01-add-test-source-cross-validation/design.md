## Context

`SourceConflictCoordinator` 已能依据 `SourceCatalog` 的对象级权威顺序输出唯一来源或 `UNKNOWN_SOURCE_CONFLICT`，但 P1 尚未提供第二个受控测试来源来实际驱动该行为。首个测试业务只读源仅用于固定查询，不能被错误地复用为两份同源候选。

## Goals / Non-Goals

**Goals:**

- 为 `test-personnel-assignment` 冻结主来源、核验来源与唯一权威顺序。
- 以固定虚构摘要生成同对象的一致、冲突、未知和核验来源不可用样本。
- 复用 `SourceConflictCoordinator`，使冲突与未知保持非确认结果。

**Non-Goals:**

- 不接入外部网络、真实源、真实身份、凭证或生产 profile。
- 不实现单源例外审批、签署替代或来源写入。
- 不由模型或样本顺序选择冲突结果。

## Decisions

1. **第二来源使用独立固定 fixture。** 核验来源在代码中拥有独立 `sourceId` 与固定摘要，避免将同一来源的重复查询误当成交叉印证。
2. **协调逻辑保持复用。** 新增测试交叉印证服务只负责查询/汇集受控候选，最终裁决交给既有 `SourceConflictCoordinator`。
3. **以冲突结果而非异常表达事实冲突。** 已登记但摘要不同的双来源候选返回 `UNKNOWN_SOURCE_CONFLICT`；只有第二来源缺失或未登记时返回明确的失败关闭语义。
4. **测试业务范围确认替代外部签署。** 固定离线虚构测试源由当前会话项目负责人确认其测试范围；记录确认方式与日期，但不伪造外部责任人签名。

## Risks / Trade-offs

- [固定第二来源覆盖有限] → 仅作为 P1 技术交叉印证，P1-006 后续增加样本类型。
- [测试范围确认被误认为生产批准] → 记录显式标记仅限 local/test，不构成 P2 或真实源授权。
- [来源顺序被修改] → TCK 锁定对象类型、两个来源 ID 和唯一权威顺序。

## Migration Plan

1. 添加第二测试来源 fixture、交叉印证应用服务和 TCK。
2. 仅 local/test 注册；prod 不注册任何测试来源。
3. 回滚时移除测试交叉印证组件与 fixture；既有协调器仍按目录失败关闭。

## Open Questions

- 无。当前会话项目负责人已确认采用测试业务范围确认，且其边界不扩展至真实源或生产。
