## Context

流程产物批次同时记录 `IMPORT_CANDIDATE` 和 `NEEDS_REPAIR` 状态。当前 ZIP 接口把导入候选状态当作下载前置条件，但人工修复场景需要先下载不完整产物再补齐流程。下载本身是只读操作，不会导入 EMS 或改变批次状态。

## Goals / Non-Goals

**Goals:**

- 有流程产物且包含 `MODEL` 文件的批次均可下载 ZIP。
- 保留批次权限、批次存在性、文件类型白名单和模型文件必选校验。
- 前端按钮状态与后端实际能力一致。

**Non-Goals:**

- 不改变 `NEEDS_REPAIR` 的业务含义。
- 不自动修复流程、不改变 BPMN 生成逻辑、不放宽流程结构校验。
- 不新增接口、数据库字段或导入 EMS 的能力。

## Decisions

1. **移除导入状态门禁，保留产物结构门禁。**
   - Controller 不再判断 `importStatus`，而是继续要求选择类型只来自白名单且必须包含 `MODEL`；缺少模型文件时仍由现有查找逻辑失败。
   - 选择该方案而不是复制一个“诊断 ZIP”接口，避免增加重复 API 和前端入口。

2. **前端按模型文件存在性启用按钮。**
   - 批次有 `MODEL` 文件时启用 ZIP；没有模型文件时保持禁用。
   - 状态标签和待补信息继续展示，用户可明确知道 ZIP 不是可直接导入包。

3. **测试覆盖两种状态。**
   - 后端 Controller 测试增加 `NEEDS_REPAIR` 仍能生成包含模型的 ZIP。
   - 保留非法类型/缺少模型的失败断言，并执行前端生产构建验证模板编译。

## Risks / Trade-offs

- [Risk] 用户可能将待修复 ZIP 误认为可直接导入 → [Mitigation] 保留“结构待修复”标签和待补信息，不改变状态含义。
- [Risk] 只下载配置文件而不含模型 → [Mitigation] 后端继续强制 `MODEL` 类型，前端仍使用模型文件名生成 ZIP 名称。

## Migration Plan

无需数据库迁移。部署前运行后端相关测试和前端构建；回滚时恢复前端状态条件和后端状态校验即可。
